## 2. תיקון שמירת התחום

### 2.1 מנגנון ההרשאות הקיים [חי]
| רכיב | מה הוא עושה |
|---|---|
| `get_my_tenant_id()` | `SECURITY DEFINER`, `search_path=public`. מחזיר את `tenant_id` מ-`agent_users` לפי `auth.uid()`. רק `authenticated` יכול להריץ |
| `tenant_access_active()` | `SECURITY DEFINER`. מחזיר true לשני חשבונות המנהל, false לעסק `cancelled`, ולעסק `trial` בודק את `trial_ends_at` |
| RLS על `tenants` | למשתמש מחובר יש רק `agents read own tenant` (SELECT). ל-`anon` אין כלום. ל-`service_role` יש הכל |
| הרשאות עמודה על `tenants` | ל-`authenticated` יש **UPDATE על כל העמודות**, כולל `plan`, `trial_ends_at`, `marketing_addon` ו-`stripe_*`. כרגע זה חסום רק בזכות ה-RLS |
| הדפוס הקיים לעדכון עסק | `update_tenant_profile`: `SECURITY DEFINER`, מזהה את המשתמש לפי `auth.uid()`, דורש `owner` או `admin`, בודק ערכים מול רשימה, ומעדכן רק את העסק של המשתמש. `anon` לא יכול להריץ |
| תפקידים בחי | 4 משתמשים, כולם `owner` |

**למה פונקציה ולא מדיניות RLS:** מדיניות UPDATE על `tenants` הייתה פותחת את כל העמודות שיש עליהן הרשאה. משתמש היה יכול לשנות לעצמו את `plan` ל-`lifetime` או להאריך את הניסיון. פונקציה צרה מעדכנת רק שני שדות, ובערכים מותרים בלבד.

### 2.2 המימוש המוצע
פונקציה אחת, באותו דפוס של `update_tenant_profile`.

**הטיוטה לא נשמרה כקובץ ב-`supabase/migrations`.** כך היא לא יכולה לרוץ בטעות, והיא תיכתב לקובץ רק אחרי אישור. בדקתי: אין workflow שמריץ מיגרציות אוטומטית [ריפו].

```sql
-- Migration 126 (טיוטה, לא הורצה): שמירת תחום העסק וסימון ההצטרפות דרך RPC צר.
-- רקע: ל-authenticated אין מדיניות UPDATE על tenants, ולכן העדכון הישיר באפליקציה
-- מעדכן 0 שורות. אין להוסיף מדיניות UPDATE רחבה: ל-authenticated יש הרשאת UPDATE
-- על כל העמודות, כולל plan, trial_ends_at ו-marketing_addon.
CREATE OR REPLACE FUNCTION public.set_tenant_industry(
  p_industry text,
  p_complete_onboarding boolean DEFAULT false
) RETURNS jsonb
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path TO 'public'
AS $$
DECLARE
  v_tenant_id uuid;
  v_role      text;
  v_result    jsonb;
BEGIN
  IF auth.uid() IS NULL THEN RAISE EXCEPTION 'not authenticated'; END IF;

  SELECT tenant_id, role INTO v_tenant_id, v_role
    FROM agent_users WHERE auth_user_id = auth.uid() LIMIT 1;
  IF v_tenant_id IS NULL THEN RAISE EXCEPTION 'no tenant for current user'; END IF;
  IF v_role NOT IN ('owner', 'admin') THEN RAISE EXCEPTION 'insufficient permissions'; END IF;

  -- אותה רשימה כמו tenants_industry_check
  IF p_industry IS NULL OR p_industry NOT IN ('realestate', 'realestate_lawyer', 'interior', 'other') THEN
    RAISE EXCEPTION 'invalid_industry';
  END IF;

  UPDATE tenants
     SET industry = p_industry,
         -- רק מ-false ל-true. הפונקציה לא מחזירה עסק לאשף
         onboarding_completed = onboarding_completed OR coalesce(p_complete_onboarding, false)
   WHERE id = v_tenant_id
  RETURNING jsonb_build_object('industry', industry, 'onboarding_completed', onboarding_completed)
    INTO v_result;

  RETURN v_result;
END;
$$;

REVOKE ALL ON FUNCTION public.set_tenant_industry(text, boolean) FROM PUBLIC, anon;
GRANT EXECUTE ON FUNCTION public.set_tenant_industry(text, boolean) TO authenticated;
```

**החלטות בתוך הטיוטה:**
- **בלי בדיקת `tenant_access_active()`:** כמו ב-`update_tenant_profile`. שינוי תחום לא נותן גישה לשום דבר, ובעל עסק שהניסיון שלו פג עדיין יכול לבחור תחום.
- **`null` לא מתקבל:** היום האפליקציה מאפסת את התחום לריק בשני מקומות: כשבוחרים "לא לשמור" ביציאה (`index.html` 14584), ובהפעלה מחדש של האשף (17796). אף אחד מהם לא עבד אף פעם, כי העדכון נחסם. בשלב 2 שניהם יעברו לשמירה דרך הפונקציה. ההצעה: להסיר את שאלת "לשמור את התחום?" ביציאה, כי התחום שייך לעסק ולא למכשיר.

### 2.3 שינויי האפליקציה (שלב 2, אחרי אישור)
| מקום | היום | אחרי |
|---|---|---|
| `DB.updateIndustry` (8094) | `sbClient.from('tenants').update(...)`, ושגיאה נבלעת | `sbClient.rpc('set_tenant_industry', ...)`, ובמקרה של שגיאה מוצגת הודעה |
| סיום האשף (9350) | שומר רק בדפדפן | `set_tenant_industry(ind, true)` |
| פתיחת האשף (14447 עד 14487) | `onboarding_done` מסומן כשיש `industry`, ו-`other` נחשב "יש" | האשף נפתח לפי `tenant.onboarding_completed === false` בשרת |
| `_getInd()` | הדפדפן גובר | `tenant.industry` גובר, והדפדפן רק שומר עותק |
| דילוג על האשף (✕) | `onboarding_done` בדפדפן | `set_tenant_industry('other', true)`, כדי שלא יחזור בכל כניסה |

**מי יראה את האשף:** רק עסקים עם `onboarding_completed = false`. בחי אלה שני עסקי הניסיון בלבד, ושניהם בלי לידים ועם שלבי ההרשמה [חי]. שני העסקים הפנימיים מסומנים `true` ולא יראו אותו. **אין צורך במיגרציית נתונים.**

### 2.4 חיזוק מומלץ, כמיגרציה נפרדת (127)
`REVOKE UPDATE ON public.tenants FROM authenticated;`
- **מה זה משנה בפועל:** כלום. ה-RLS כבר חוסם כל עדכון, וגם המענק מ-029 (`UPDATE (onboarding_completed)`) לא עבד בלי מדיניות.
- **למה בכל זאת:** שכבת הגנה נוספת. אם מישהו יוסיף בעתיד מדיניות UPDATE בטעות, משתמשים לא יוכלו לשנות לעצמם את `plan`.
- **תנאי:** לפני כן מוודאים שאין בקוד עדכון ישיר אחר של `tenants`. בדקתי בריפו: היחיד הוא `DB.updateIndustry`, שעובר לפונקציה.
- זה שינוי הרשאות, ולכן דורש אישור נפרד.

### 2.5 בדיקות נדרשות
**א. סטטיות, בריפו וב-CI (בלי DB):**
- קובץ חדש `supabase/tests/tenant-industry-rpc.test.ts`, באותו סגנון כמו בדיקות `notify-owner`. הוא יוודא:
  - שהמיגרציה כוללת `SECURITY DEFINER` ו-`SET search_path`.
  - שיש בדיקת `owner` או `admin`.
  - שרשימת התחומים זהה ל-CHECK.
  - שיש `REVOKE` מ-`PUBLIC` ומ-`anon`, ו-`GRANT` ל-`authenticated`.
  - שב-`index.html` אין `.from('tenants').update(`.
  - שאין קריאה בתבנית `sbClient.rpc(...).catch(` (סעיף 4).

**ב. לפני הרצה, בחי, קריאה בלבד:**
- שאין כבר פונקציה בשם `set_tenant_industry`, ושאין overloads.
- שה-CHECK על `tenants.industry` לא השתנה.
- השוואה ל-`update_tenant_profile`, כדי לשמור על אותו דפוס.

**ג. אחרי הרצה, באישורך, בתוך טרנזקציה שמבוטלת בסוף (ROLLBACK), כך ששום נתון לא משתנה:**
1. הרשאות: `anon` לא יכול להריץ, `authenticated` יכול, ויש overload אחד בלבד.
2. משתמש `owner` (בסימולציה): הקריאה מחזירה את התחום החדש. נבדק שרק השורה של העסק שלו השתנתה, ושל העסקים האחרים לא.
3. משתמש מחובר בלי עסק: השגיאה "no tenant".
4. משתמש בתפקיד `agent`: השגיאה "insufficient permissions". אין היום משתמש כזה, ולכן צריך ליצור שורה זמנית בתוך הטרנזקציה המבוטלת. זה דורש אישור מפורש.
5. ערך לא חוקי, ו-`null`: השגיאה "invalid_industry".
6. `onboarding_completed` לא חוזר מ-true ל-false.
7. עדכון ישיר של `tenants` עדיין מעדכן 0 שורות.
8. יועצי האבטחה של Supabase אחרי ההרצה.

**ד. בדפדפן, במוק (התשתית ב-`scripts/`):**
- האשף נפתח לעסק עם `onboarding_completed = false` ולא נפתח לעסק עם `true`.
- בחירת תחום שולחת את הפונקציה, ואחרי טעינה מחדש התחום נשאר, גם אחרי ניקוי `localStorage` (כמו "מכשיר אחר").
- כשהפונקציה נכשלת, מוצגת הודעה.
- רגרסיה: `smoke-390` ו-`test-ux-interactions`.

**חזרה לאחור:** `DROP FUNCTION public.set_tenant_industry(text, boolean);`, והחזרת הקוד ב-git. ערכי `industry` שנשמרו בינתיים נשארים תקינים, כי הם בתוך ה-CHECK. בשביל 127: `GRANT UPDATE ON public.tenants TO authenticated;`.

## 3. מכסות AI והוצאות

### 3.1 מה מגביל את ההוצאה היום [חי, ריפו]
- **נקודת יציאה אחת:** רק `ai-proxy` פונה ל-Anthropic. אף פונקציה אחרת ואף משימה מתוזמנת לא פונות.
- **הקוד שרץ זהה לריפו:** `ai-proxy` גרסה 40, נפרסה מה-CI, והקוד שבה זהה לריפו.
- **הזדהות:** הפונקציה דורשת משתמש מאומת (`getUser`).
- **מכסה לפני כל קריאה:** המכסה נבדקת ונספרת בשרת (`check_and_increment_ai_usage`, עם `FOR UPDATE` על השורה היומית) לפני הפנייה ל-Anthropic. שימוש שחורג נחסם ב-429.
- **מודלים:** רק `claude-sonnet-4-6` ו-`claude-haiku-4-5-20251001`. ברירת המחדל Haiku. ייבוא מתמונה תמיד Haiku.
- **תקרות לכל קריאה:**
  - פלט: עד 1,000 טוקנים, ובייבוא מתמונה עד 1,500.
  - קלט: עד 6 הודעות של 4,000 תווים, ועוד הנחיית מערכת של 2,000 תווים.
  - תמונה: אחת, עד כ-3.3MB.
- **מכסות שבועיות:** ייבוא מתמונה 2 בשבוע, טקסט לדף לקוח (`page_copy`) 5 בשבוע.
- **שימוש בפועל [חי]:**
  - `ai_usage` ריקה. אין שימוש רשום מאז שהטבלה קיימת.
  - אין שימוש בייבוא מתמונה וב-`page_copy` ב-30 הימים האחרונים.

### 4.2 הסיבה: שתי בעיות נפרדות
**א. באפליקציה (`index.html`) המעקב לא נשלח אף פעם.** [ספרייה, ריפו]
- **הקוד:** `FunnelTracker.track` קורא `sbClient.rpc('track_funnel_event', ...).catch(() => {})`.
- **הבעיה:** בגרסת הספרייה שהאפליקציה טוענת (`@supabase/supabase-js@2.108.2`), האובייקט ש-`rpc()` מחזיר תומך ב-`then` ולא ב-`catch`. הבקשה יוצאת רק כש-`then` נקרא.
- **בבדיקה מבודדת:** `rpc(...).catch` זורק `TypeError` מיד, ו-0 בקשות נשלחות. אותה קריאה עם `await` שולחת בקשה אחת.
- **למה זה לא נראה:** ה-`TypeError` נבלע ב-`try/catch`. GA4 ממשיך לקבל את האירוע, אבל ה-DB לא מקבל אף פעם.
- **התאמה ללוגים:** 2 כניסות לאפליקציה ב-24 שעות, ו-0 קריאות מעקב.

**ב. בדף הנחיתה המעקב תקין, אבל לא היו לחיצות.**
- **מה בדקתי:** בדיקת Chromium עם Supabase מדומה מקומית, בלי לגעת ב-DB האמיתי. לחיצה על כפתור ה-Hero שלחה `POST` ל-`track_funnel_event` עם `landing_cta_click`.
- **מה ראיתי בחי:** 6 טעינות ב-24 שעות, בלי לחיצה.
- **[מסקנה]:** אין לחיצות של מבקרים מאז ה-15.10, או שהן מדפדפנים אחרים. לא בדקתי Safari ו-Firefox.

### 4.3 ממצא נוסף מאותו סוג
- **המקום:** `index.html` 19671: `await sbClient.rpc('mark_lead_tracker_messages_read', ...).catch(() => {})`, בתוך `LeadTracker.open`.
- **מה קורה, לפי הקוד והספרייה:** ה-`TypeError` נזרק ונתפס ב-`catch` של הפונקציה. לכן אחרי יצירת קישור מעקב ללקוח מוצגת "שגיאה ביצירת הקישור, נא לנסות שוב", למרות שהקישור נוצר. גם `loadUpdates()` לא רץ.
- **מה לא בדקתי:** את ההתנהגות בדפדפן מול השרת.
- **מה עובד:** `append_audit` משתמש ב-`.then(() => {}).catch(...)`, ולכן הוא עובד. בלוגים מופיעות 2 קריאות שלו עם 204.

### 4.4 התיקון המוצע (שלב 2, אחרי אישור)
- **החלפה:** בשני המקומות, `.catch(() => {})` מתחלף ב-`.then(() => {}, () => {})`. זו אותה צורה שכבר עובדת ב-`append_audit`.
- **בדיקה סטטית:** בדיקה שתמנע את הדפוס הזה בעתיד (2.5 א).
- **שינוי קוד בלבד,** בלי שינוי ב-DB. Level 1.
- **אחרי התיקון:** אירועי האפליקציה יתחילו להירשם ב-`funnel_events`. אלה נתונים טכניים (אירוע, מזהה סשן, מזהה עסק). כדאי לוודא שמדיניות הפרטיות מכסה אותם.
