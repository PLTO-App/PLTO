# תוכנית: העברת האתר מ-realestate.plto.app לתת-דומיין חדש (2.11.2026)

**סטטוס (2.11.2026, לילה): אושר. השם `sales.plto.app`, ואיפוס הנתונים שנשמרים רק בדפדפן מאושר. שלב 1 בביצוע (PR עם CORS ודף הנחיתה). שלבים 2 עד 6 עוד לא בוצעו.**

**ממצא בזמן שלב 1:** בגרסה החיה של `gmail-proxy` ושל `twilio-whatsapp` לא הייתה הכתובת `realestate.plto.app` ברשימת ה-CORS. בבדיקת OPTIONS מהכתובת הזו שתיהן החזירו `Access-Control-Allow-Origin: https://plto.app`, ולכן הדפדפן חוסם את הבקשות מהאתר החי. השינוי נכנס לריפו ב-#151 ולא נפרס, כי workflow הפריסה האוטומטית מעלה רק את `ai-proxy` ואת `notify-owner`. מלבד השורה הזו הקוד החי זהה לריפו. הפריסה בשלב 1 סוגרת את זה.

השם שנבחר: `sales.plto.app`. בהמשך המסמך `NEW` הוא `sales.plto.app`.

רמת שינוי: 3 (הגדרות פרודקשן, כניסה עם Google, קישורים ציבוריים). לכן תוכנית, אישור, ביצוע בשלבים ובדיקה.

## מה נבדק (קריאה בלבד)

- DNS של `plto.app` מנוהל ב-Cloudflare. `realestate` הוא CNAME ל-`plto-app.github.io` בלי Proxy. `sales` ו-`selas` לא קיימים.
- האתר מוגש ב-GitHub Pages. לאתר כזה יש דומיין מותאם אחד בלבד (קובץ `CNAME`).
- הכתובת הישנה מופיעה ב-25 קבצים: האפליקציה, דף הנחיתה, `sign.html`, `page.html`, `track.html`, `portfolio.html`, `admin.html`, מדיניות הפרטיות, `sitemap.xml`, `robots.txt`, ארבע פונקציות Edge (רשימת CORS), שתי בדיקות ובדיקת דף הנחיתה.
- ב-DB החי: רק `create_client_page` בונה קישור עם הכתובת (מיגרציה 120). אין שורות שמורות ב-`client_pages.cta_url` עם הכתובת, ואין משימות cron שתלויות בה.
- `gmail-oauth-callback` ו-Twilio עובדים מול כתובת Supabase ולא מול האתר, ולכן לא מושפעים.

## השפעות שחשוב לדעת לפני ההחלטה

1. **כל המשתמשים יתנתקו פעם אחת.** החיבור ל-Supabase שמור בדפדפן לפי כתובת האתר. בכתובת החדשה נכנסים מחדש (6 משתמשים היום).
2. **נתונים שנשמרים רק בדפדפן יתאפסו:**
   - XP, הישגים וחבילות שנפתחו (`plto_gamify_v2`) נשמרים רק בדפדפן.
   - תבניות הודעה אישיות (`pro_templates`).
   - קוד ה-PIN המקומי ונעילת המסך, שצריך להגדיר מחדש.
   - העדפות מקומיות (סגנון WhatsApp, סיור היכרות שכבר הוצג).
   לידים, לקוחות, משימות ונתוני העסק שמורים בשרת ולא נפגעים. בפועל זה נוגע בעיקר לעסק של דקלה. כדאי להודיע לה מראש.
3. **קישורים שכבר נשלחו ללקוחות** (הסכם הפניה ב-`sign.html`, עמודי לקוח, מעקב, ויטרינה, קישורי הפניה והסכמה) חייבים להמשיך לעבוד. לכן הכתובת הישנה תעבור להפניה קבועה לכתובת החדשה, עם הנתיב וה-query string.
4. **אפליקציה מותקנת (PWA)** על הכתובת הישנה תיפתח, תופנה לכתובת החדשה ותעבוד בדפדפן. כדי לקבל אייקון חדש צריך להתקין מחדש.

## סדר הביצוע

### שלב 1: הכנה בלי השבתה (קוד)
- להוסיף את `https://NEW` לרשימות ה-CORS בארבע פונקציות Edge (`ai-proxy`, `gmail-proxy`, `notify-owner`, `twilio-whatsapp`), ולהשאיר בינתיים את הכתובת הישנה. לפרוס ולבדוק.

**מצב שלב 1 (3.11.2026): הושלם.** PR #192 ו-#193 מוזגו. ארבע פונקציות Edge (`ai-proxy`, `gmail-proxy`, `notify-owner`, `twilio-whatsapp`) פרוסות ועונות CORS ל-`sales.plto.app` ול-`realestate.plto.app`, ולמקור זר הן עונות את הכתובת הישנה. נבדק בחי ב-OPTIONS. בקשה בלי אימות עדיין מחזירה 401, ו-`ai-proxy` עדיין חוסם עם 503 (מתג הכיבוי). הפריסה בוצעה ידנית דרך חיבור Supabase, כי הפריסה האוטומטית נכשלת:
- הפריסה האוטומטית נכשלת ב-403 מ-Supabase ("Your account does not have the necessary privileges") לפחות מאז 22.10, והצליחה בפעם האחרונה ב-15.10. 403 ולא 401 אומר שהטוקן `SUPABASE_ACCESS_TOKEN` מוכר, והחשבון שמאחוריו כנראה לא מורשה בפרויקט (משוער, לא אומת).
- 2.11: ה-CLI העדכני דורש גם `--yes` בסביבה בלי טרמינל, וזה הסתיר את ה-403. תוקן ב-#193 (`--yes` ו-`workflow_dispatch`). **פתוח לדוד:** ליצור Access Token חדש בחשבון Supabase ולעדכן את ה-Secret. עד אז כל שינוי בפונקציות דורש פריסה ידנית, וכל מיזוג שנוגע בהן יתריע בכשל.
- לפני הפריסה ידנית הושוו `ai-proxy` ו-`notify-owner` החיים לריפו, והיה הבדל אחד בלבד: שורת ה-CORS. ב-`gmail-proxy` וב-`twilio-whatsapp` החיים חסרה גם `realestate.plto.app`, וזה תוקן.

### שלב 2: הגדרות אצל דוד (לפני ההחלפה)
- **Cloudflare, DNS:** רשומת CNAME בשם `sales` (או השם שנבחר) אל `plto-app.github.io`, במצב DNS only (ענן אפור).
- **Supabase, Authentication, URL Configuration:** להוסיף את `https://NEW/` ו-`https://NEW/**` ל-Redirect URLs. את ה-Site URL מחליפים בשלב 4.
- **Google Cloud Console:** לבדוק אם במסך ההסכמה של OAuth או ב-Authorized JavaScript origins מופיעה הכתובת הישנה, ולהוסיף את החדשה. כתובת החזרה עצמה היא של Supabase ולא משתנה.

### שלב 3: ההחלפה (commit אחד, PR אחד)
- `CNAME` מקבל את השם החדש.
- כל ההפניות בקוד מוחלפות לכתובת החדשה: כתובת החזרה של Google, קישורי הפניה, הסכמה, עמודי לקוח, תגי OG, `sitemap.xml`, `robots.txt`, מדיניות הפרטיות ו-`README`.
- מיגרציה 131: `create_client_page` בונה את `cta_url` על הכתובת החדשה. מריצים אותה רק באישור.
- עדכון הבדיקות (`test-landing`, בדיקות ה-Edge) והרצת כל סט הבדיקות.
- אחרי המיזוג: ב-GitHub, Settings, Pages, לוודא שהדומיין התעדכן ולסמן Enforce HTTPS כשהתעודה מוכנה (בדרך כלל דקות, לפעמים עד שעה).

### שלב 4: הפניה מהכתובת הישנה (דוד, מיד אחרי שהחדשה עולה)
- **Cloudflare:** להפעיל Proxy (ענן כתום) על `realestate`, ולהוסיף Redirect Rule: Hostname שווה `realestate.plto.app`, הפניה דינמית 301 אל `concat("https://NEW", http.request.uri.path)` עם Preserve query string.
- באותו מקום: `plto.app` ו-`www.plto.app` אל `https://NEW/landing.html`, עם שמירת query string.
- **Supabase:** Site URL יוחלף ל-`https://NEW/`. את הכתובת הישנה אפשר להשאיר ב-Redirect URLs לתקופת מעבר.

### שלב 5: בדיקה
- בדפדפן מול האתר החי ב-390px: דף הנחיתה, כפתורי הרשמה עם UTM, ומסך כניסה בכתובת החדשה.
- הפניות: `realestate.plto.app/sign.html?lref=x` מגיע ל-`NEW/sign.html?lref=x`, וכך גם `page.html`, `track.html` ו-`portfolio.html`.
- CORS: הפונקציות עונות לכתובת החדשה.
- כניסה עם Google בטלפון בכתובת החדשה, עד מסך "היום". זו גם משימה 11 ביומן, ואפשר לסגור את שתיהן בבדיקה אחת.

### שלב 6: ניקוי (אחרי כמה שבועות)
- להסיר את הכתובת הישנה מרשימות ה-CORS ומ-Redirect URLs. את ההפניה ב-Cloudflare משאירים לצמיתות.
